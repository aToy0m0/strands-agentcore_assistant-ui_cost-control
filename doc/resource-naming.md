# リソース名・名前空間の設計

## 1. 目的

AWSマネジメントコンソールで見たときに、どのスタックに属するリソースか分かるよう、CDKが作成する各リソースへ共通のプレフィックスを付ける。

利用者はconfigファイルに元の名前を1つだけ設定する。小文字版、ハイフンをアンダースコアへ置き換えた版、スラッシュを付けた版、一意性用ハッシュを付けた版などを設定ファイルで管理する必要はない。各サービスの命名制約への変換と一意性の確保はCDK側で行う。

`agentcore-cost-control`など特定の固定値への統一を目的にしない。表記がサービスごとに多少変わっても、共通名から所属を判別できればよい。CDKやAWSが自動付与するハッシュ・接尾辞は許容する。

本書は現在の実装仕様を示す。

## 2. 利用者が設定する値

既存JSONのcamelCaseに合わせ、設定キーを次のようにする。

```json
{
  "defaultCdkPrefix": "Agent-Core-Runtime_Cost-control",
  "runtimeDisplayName": "AIエージェント"
}
```

| フィールド | 用途 |
|---|---|
| `defaultCdkPrefix` | スタックとCDKが作るリソースの名前に使う共通入力。大小文字、数字、ハイフン、アンダースコア、空白を受け付ける |
| `runtimeDisplayName` | 日本語や記号を含められるアプリ表示名。AWSリソース名の生成には使わない |

`runtimeDisplayName`はAWSの`agentRuntimeName`とは別のアプリ表示用設定である。表示名だけを変更しても、リソース名やデータの識別子は変わらない。

旧命名キーは受け付けず、同じ意味の設定を二重管理しない。認証、モデル、リージョンなど、命名以外の設定は引き続き必要となる。

## 3. CDKが引き受ける処理

名前は原則として「共通プレフィックス＋リソースの用途」から作る。グローバルな一意性が必要なCognito提供ドメインだけはStack由来の環境識別子を加える。サービスによって区切りや順序の制約がある場合は、その制約に合わせる。

| 対象 | CDK側の処理 | 生成イメージ |
|---|---|---|
| スタック | 共通入力からスタック名を生成 | `agent-core-runtime-cost-control-stack` |
| Cognito User Pool・Client | 共通名に用途を追加 | `agent-core-runtime-cost-control-users`、`agent-core-runtime-cost-control-web` |
| AgentCore Runtime・Memory | 区切りをアンダースコアへ変換して用途を追加 | `agent_core_runtime_cost_control_runtime` |
| Gateway・Lambdaなど | 対象の許容文字に変換して用途を追加 | `agent-core-runtime-cost-control-tools` |
| KMS Alias | 必須のパスを追加 | `alias/agent-core-runtime-cost-control-memory` |
| 管理するロググループ・名前空間 | 対象の形式に応じてスラッシュや用途を追加 | `/agent-core-runtime-cost-control/...` |
| Cognitoのプレフィックスドメイン | 共通名とCloudFormation Stack IDのUUID先頭8文字を結合 | `agent-core-runtime-cost-control-<stack-id先頭8文字>` |
| CDK補助Lambdaなど | 共通名を含むスタック名を通じて自動生成 | `<スタック名>-<用途>-<CDK/AWSの接尾辞>` |

この表は生成方針であり、全サービスに同じ文字種や構造を強制するものではない。例えば小文字化は統一した生成規則として採用できるが、すべてのサービスが大文字を禁止しているという意味ではない。

### 表記と長さ

- 前後の空白を除き、大小文字や区切り文字を対象に合わせて正規化する。連続した区切りは1つにまとめる。
- 英字始まりが必要な対象で先頭が数字になる場合は、定めた英字接頭辞を補う。
- 用途やハッシュを含めた最終名が上限内になるよう、必要な場合だけ共通部分を短縮する。短縮時は元の名前を識別する安定したハッシュを残す。
- 空文字や許可外の入力は、設定キーと原因を示してエラーにする。日本語を技術名へ自動翻訳したり、固定名へ暗黙的に置き換えたりしない。
- 各対象の最終名を検証する。Runtime名は[CloudFormationの公式仕様](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-bedrockagentcore-runtime.html)などを参照し、実装時に対象ごとの制約を確認する。

### Cognitoドメイン用の環境識別子

利用者にハッシュの生成・転記・保存を求めない。CDK/AWSの自動生成で一意性を確保できる対象は、その仕組みを使う。Cognitoのプレフィックスドメインだけはグローバルに一意である必要があるため、`<基準名>-<環境識別子8文字>`とする。

環境識別子はCloudFormation Stack IDに含まれるUUIDの先頭8文字を使う。同じスタックを更新する限り変わらず、スタックを削除して再作成すると変わる。AWSアカウント、リージョン、基準名を材料に独自の環境ハッシュは生成しない。

8文字の識別子は衝突確率を下げるもので、外部で既に取得された名前の利用可能性を保証しない。競合時に勝手な別名で再試行せず、対象と原因を示す。

同じアカウント・リージョンで別の環境を作る場合は、共通入力に環境を区別する文字列を含める。正規化後に同じになる入力は、別環境の識別には使えない。

## 4. 共通プレフィックスを付ける範囲

直接管理するリソースのマネコン上の名前を対象にする。Cognito、Runtime、Memory、Gateway、Lambda、DynamoDB、S3、IAM Role、KMS Alias、Dashboard、管理するロググループなどについて、共通名から所属を判別できることを確認する。

自動生成名が共通名を含む場合は明示名を追加しない。自動生成名では所属が分からない対象には、CDK側で生成した名前を明示する。固定名の指定による置換制約も含めてdiffで確認する。

スタック名もconfigから生成する。TypeScriptのクラス名やConstruct IDは実装上の識別子として安定させ、表示上の統一のためだけには変更しない。

CDK補助リソースは共通名を含むスタック名からの自動生成を活用する。AWS発行のID、CloudFormation論理ID、サービス管理ログの既定パスなど、名前を制御できない対象は例外とする。タグを付けられる対象では共通タグも併用するが、名前で識別できる対象は名前にも反映する。

生成規則はCDK側の小さな命名モジュールへ集約する。アプリが使う名前・名前空間は環境変数や画面設定などで受け渡し、デプロイスクリプト、Runtime、フロントエンドで変換を重複実装しない。AWSリソースの参照にはCDK参照やOutputを使う。

## 5. 個別設定が必要な例外

文字種、区切り、長さ、一意性用接尾辞の違いだけでは設定フィールドを増やさない。CDK側の変換では解決できない条件に限り、個別設定を設ける。

| 対象 | 個別に設定する理由 |
|---|---|
| `runtimeDisplayName` | 利用者に見せる日本語名を技術名とは独立して決めるため |
| カスタムドメイン・証明書・Hosted Zone | DNSの所有権や既存証明書との対応は共通名から決められないため |
| 既存Knowledge BaseやSecretなどの参照 | 外部リソースのID・ARN・名前を指定するため |

Cognitoドメインの予約語などは[公式仕様](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-assign-domain.html)に従って検証し、生成できない場合は対象と原因を示す。

Memory名前空間と費用集計IDは共通名から導出する。今回は旧環境を削除して新規デプロイするため、既存データとの互換設定や移行用フィールドは設けない。

全リソース向けの上書きフィールドを先回りして作らない。AG-UIのイベント名、ツール名などの通信契約も、マネコンでの識別を目的とする今回の変更には含めない。

## 6. 現在の実装

- `infrastructure/app.ts`はconfigからStack名を生成する。
- 共通名は大小文字と区切り文字を受け付け、対象サービスの制約に合わせて変換・検証する。
- Cognito、Runtime、Memory、Gateway、Lambda、KMS Alias、Metric Namespace、Dashboard、管理ロググループは同じ命名規則を使う。
- CDKが物理名を生成するS3、DynamoDB、IAM Role、補助Lambdaは、共通名を含むStack名から所属を判別できる。
- 表示名はRuntime設定を介して画面へ渡し、技術名の生成には使わない。

## 7. 既存環境への適用

今回は旧環境を削除して新規デプロイする。Cognitoユーザー、Memory、費用集計、旧URLは移行しない。新しいカスタムドメインはconfigの`customDomainName`へ個別指定する。

## 8. 受入条件

- configの共通名1か所から、マネコン上で各リソースの所属スタックを判別できる名前が生成される。
- 大小文字混在・ハイフン・アンダースコアを含む入力を、対象別の制約へ機械的に変換できる。
- 利用者が変換済みプレフィックスやハッシュをconfigへ列挙する必要がない。
- Cognitoの環境識別子は同じスタックの更新で安定し、削除・再作成時だけ変わる。
- 日本語を含む表示名を正しく表示でき、表示名だけの変更で技術名が変わらない。
- 長い入力、数字始まり、連続区切り、無効入力について、定めた変換または明確なエラーを確認できる。
- 自動生成名を含めてsynthで確認し、名前を制御できない対象の例外を明示できる。
- diffで作成・更新・置換・削除と既存データへの影響を確認できる。
